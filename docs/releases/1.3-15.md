# Departs 1.3 (15) TestFlight

New builds of Departs Now use `https://api.departs.now` for transit data and walking routes. Installed builds keep using the Vercel hostname compiled into them. The marketing version is 1.3 and the build number advances to 15.

## What changes since 1.3 (14)

- The production URL builder and the default client use the new hostname. Debug launch environments can still override the host for fixture tests.
- An HTTP 500 uses the same temporary-failure path as an HTTP 502. An HTTP 429 triggers one retry. The client waits for `Retry-After`, capped at five seconds, or waits two seconds when no valid value is present. A second refusal goes through the temporary-failure path.
- The app caches successful, validated stop lists for 24 hours and walking routes for one hour by exact request URL. It retains those lifetimes when the host omits cache headers or sends `private, no-store`. Both departure requests still bypass the local cache.
- At most four API requests can be in flight at once. Identical requests continue to share one response. Waiting to retry a 429 frees the request slot for other calls.

## What to test

At a station, open Departs Now and check the nearby list. Open a line for its individual departures and verify the walk on the line screen. Pin it, relaunch the app and open it again. Pull to refresh and check that departures update.

## Rider behaviour

All four calls already treated every non-200 response as a temporary failure before decoding the body. Today a 500 with the backend's JSON error and an exhausted 429 with HTML lead to the following existing behaviour.

| Request | Rider experience after a temporary failure | Cache behaviour |
| --- | --- | --- |
| Nearby stops | The first failure shows “Couldn't update nearby stops” and “Try again”. A failure refreshing the same area keeps its stops and tries to update their departures. | The last area is saved separately from HTTP. The client now supplies the original 24-hour lifetime for an identical nearby query. |
| Batch departures | Home shows a retry when there's no saved board. An existing board stays visible with its saved times and a refresh button. | The app saves boards locally, uses the API timestamp for freshness and always requests departures without reading the local HTTP cache. |
| Line departures | The line shows a retry with no saved board, or keeps its saved times and offers a refresh. | The app saves the last board and always requests departures without reading the local HTTP cache. |
| Walking route | Departures remain visible. Without a valid route, the line map can still show its origin and platform. | The store already reuses recent walks for ten minutes near the same origin. The client now also retains the original one-hour lifetime for an identical walking query. |

### Finding on stale departure responses

The backend trial reported three stale HTTP 200 batch responses, about 138 to 381 seconds old. Spacefast now serves departures with `Cache-Control: no-store`, so its shared cache no longer serves expired departure boards. The app behaviour below describes what the trial exposed. Its freshness limit is 60 seconds inclusive in `DepartureBoard.isFresh(at:)` in `TransitState.swift`. The shared date helper also tolerates timestamps up to five seconds ahead of the device clock.

- **Batch.** `TransitStore.refreshAnswers` uses the server's `fetchedAt` for the board and home snapshot. A valid timestamp older than 60 seconds is accepted as saved data. Home shows a “Saved times from … · Refresh” banner and clock times without live countdowns. The partial-board retry message takes precedence when platforms are missing. A row can show a departure whose time has already passed because the saved row uses the first returned time. A detail screen still using that batch also shows saved times. The app sets no request error and starts no immediate retry on account of age. The rider can refresh manually, and the foreground refresh loop waits 30 seconds between passes. Ordinary batch refresh requests are suppressed through 25 seconds after the last attempt.
- **Per line.** The response is an array of departures with no server `fetchedAt`. `TransitStore.refreshBoard` stamps the board with the local receipt time. Even if the host served an old response from cache, a still-upcoming departure can show a fresh countdown and live indicators. Departures that have passed by receipt are filtered out. The server's actual response age does not trigger an error, stale marking or extra fetch.

Two temporary iPad simulator unit tests passed. The batch test used 60-, 138- and 381-second-old boards and checked the cutoff, saved clock presentation, lack of an error or immediate fetch, and the ordinary refresh guard. The line test checked receipt-time freshness through 60 seconds and the live countdown. The probes verified existing behaviour. No production code or tests were changed for this finding.

### Production hostname, 26 November 2026

Direct curl requests verified the certificate chain and the hostname `api.departs.now`. The certificate expires on 23 February 2027 at 22:01:22 UTC. Plain HTTP returned 301 to the same URL on HTTPS.

The app's 400 m requests returned 17 stops in Vienna and 28 at Berlin Alexanderplatz. The custom Spacefast hostname, its managed hostname and Vercel returned identical stop records and walking routes. All three returned boards for the same 17 Vienna platforms and the same 24 Berlin platforms, with the other four Berlin IDs in `missing`. Batches contained the same 28 Vienna and 125 Berlin service groups. Individual predictions changed between reads as departures passed. Each per-line response contained only the requested service. All four request forms returned HTTP 200 and `application/json` in both cities.

All 30 custom-host batch responses (15 per city) returned `Cache-Control: no-store` and `X-ac: … MISS`. The oldest `fetchedAt` at receipt was 0.703 seconds in Vienna and 0.657 seconds in Berlin. Per-line responses also returned `no-store` and MISS. The per-line wire format has no timestamp. Stops returned `public, max-age=86400` and walks returned `public, max-age=3600`. Vercel retained `public, max-age=30` for departures.

| Request | Custom hostname, median / worst | Managed hostname, median / worst |
| --- | ---: | ---: |
| Nearby stops | 626 / 958 ms | 672 / 798 ms |
| All-platform batch | 783 / 855 ms | 700 / 944 ms |
| Per-line departures | 599 / 867 ms | 660 / 1,041 ms |
| Walking route | 410 / 808 ms | 484 / 588 ms |

Each latency cell covers ten anonymous, uncached curl requests, split equally between the cities. Every response reported MISS. Stop and walk samples used a distinct query value to force a miss. Durations include starting a fresh connection. Requests to all three hosts ran in sequence, at least two seconds apart.

The live stop records omit `distance` and line `id` on all three hosts. Both fields are required in `app/types.ts`. The Swift model accepts an absent distance and derives line identity from its name and direction. The batch envelope and walking geometry matched their Swift models. Neither has a declaration in `app/types.ts`. The new host returned 400 with `{"error":"Missing stopId parameter"}` for a missing stop parameter, 200 with an empty board list and the unknown ID in `missing` for an unknown station, and 500 with `{"error":"No walking route found"}` for a walk across open sea.
